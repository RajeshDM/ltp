\section{Appendix}

This appendix gives the detail a reader needs to implement the
representation, reproduce the experiments, or reuse either in another
setting. It adds no results: everything reported in the paper is in the
paper.

\subsection{Building the Graph}
\label{app:pseudocode}

Algorithm~\ref{alg:graph} constructs $\mathcal{G} = (V, E, X, R)$ for one
task, in the notation of the representation section. Lines marked $\dagger$
depend on the domain description alone, so they are computed once per domain
and reused for every state of it; the rest are per state and are linear in
the applicable groundings and the open goal atoms. The three systems are
prefixes of the same procedure: \union{} runs lines 1 to 3 with
symbol-identity features in place of $X$, \gadarbind{} runs lines 1 to 7, and
\gadar{} runs all of it.

\begin{algorithm}[h]
\caption{Construction of the \gadar{} graph for $(s, G, D)$}
\label{alg:graph}
\begin{algorithmic}[1]
\STATE $V \leftarrow O \cup L \cup A \cup \{g\}$ where $L$ holds the ground
  literals of $s$ and of $G$, the latter flagged as goal atoms
\STATE add $E_{\mathrm{lit}}$: each literal to its argument objects, argument
  position on the edge
\STATE add $E_{\mathrm{act}}$: each schema to the objects of its
  \emph{applicable} groundings, parameter slot on the edge
\STATE $\dagger$ compile each declared PDDL type of $D$ into a unary static
  predicate, so typed and predicate-typed domains present one structure
\STATE $\dagger$ $V \leftarrow V \cup \Sigma \cup Q$: a node per predicate
  symbol of $D$, and an occurrence node $q_{a,k}$ per literal occurrence in
  the preconditions and effects of each schema $a$
\STATE $\dagger$ add $E_{\mathrm{occ}}$: each occurrence to its predicate
  symbol and its schema, carrying role $r(q)$ and argument-to-slot pairs
\STATE add $E_{\mathrm{inst}}$ and $E_{\mathrm{bind}}$: each literal to its
  predicate symbol, each object to its type symbol, and $(o, q_{a,k})$
  whenever an applicable grounding of $a$ puts $o$ at a slot that occurrence
  $k$ constrains
\STATE $\dagger$ add $E_{\mathrm{chain}}$: \textit{enables} between an add and
  a pre occurrence of a shared predicate, \textit{threatens} likewise for del
\STATE add $E_{\mathrm{eff}}$: from each applicable grounding, link its
  objects to any unsatisfied goal atom it adds and any true atom it deletes
\STATE compute $\mathrm{gdist}(a)$ by breadth-first search over
  \textit{enables} from the schemas adding a goal predicate; mark objects
  occurring in an open goal atom
\STATE emit $X$ and $R$ as indicator vectors; widths depend only on the global
  arity caps $(k_p, k_a)$, never on $|A|$, $|P|$, $|T|$ or $|O|$
\end{algorithmic}
\end{algorithm}

Two implementation points matter for anyone rebuilding this. First, the type
compilation on line 4 is what lets one model span domains that declare PDDL
types and domains that spell types as ordinary unary predicates; without it
the two families present different structure for the same constraint, and a
policy trained on one produces type-invalid groundings on the other. Second,
$E_{\mathrm{bind}}$ on line 7 is the only relation that crosses between the
two layers, joining an object of the current problem to a precondition
occurrence of a schema in $D$. Everything else lives wholly inside one layer.

The reference implementation accumulates edge features sparsely, as a map
from node pair to the set of features that hold. A dense
$(k_a, |V|, |V|, \dim R)$ array is the obvious alternative and is what we
wrote first, but it costs $O(k_a |V|^2 \dim R)$ to allocate and scan for
every state, which dominates the cost of re-featurizing states during
evaluation on large instances.

\subsection{Decoding and Training}
\label{app:decode}

A GRU scores the schema nodes against its hidden state and takes the best,
then scores the object nodes once per argument of the selected schema,
feeding each choice back as the next input. The number of arguments is read
from $D$ for the selected schema, under a global arity cap rather than a
per-domain constant, which is what allows the loop to run in a domain whose
schemas were never seen. Selection is a dot product between the decoder state
and the embedding of a node present in the graph, so no layer is sized by the
number of schemas, objects, or predicates. Search over these choices is a
beam of width 2 over schemas and 3 over objects per slot.

Training is supervised on plans from a satisficing planner: cross-entropy
against the planner's schema choice and each of its argument choices, at
every state along every plan. Because feature widths do not depend on the
domain, states from different domains mix freely within a batch.

\subsection{Hyperparameters}
\label{app:hyper}

Table~\ref{tab:hyper} lists every setting. Encoder and decoder
hyperparameters are inherited from \citet{gabar} without modification. This
is deliberate rather than incidental: the comparisons in the paper are
between representations, and re-tuning the network for each one would
confound them. We therefore ran no architecture search, and a practitioner
adapting this to a new benchmark should expect to gain from tuning we did not
do. The two settings we did choose are the global arity caps $(k_p, k_a)$,
set to the maxima over the training domains so a held-out domain with wider
symbols still featurizes at full width, and the number of training epochs.

A run is seeded once, and that seed governs the network initialization, the
training shuffle, the train and validation split, and the revisit monitor's
fallback sampling. Each reported configuration is run for three seeds and the
results averaged. We report means without dispersion: three runs are too few
for a meaningful interval, and the differences the paper turns on are far
larger than the spread we observe.

\subsection{Evaluation Protocol}
\label{app:metrics}

Let $\mathcal{T}$ be a test set and $\mathrm{solved}(\pi) \subseteq
\mathcal{T}$ the instances on which policy $\pi$ reaches a goal state within
the execution bound. \emph{Coverage} is
\begin{equation*}
C(\pi) \;=\; \frac{|\mathrm{solved}(\pi)|}{|\mathcal{T}|} \times 100 .
\end{equation*}
Execution is greedy and search-free. At each state the highest-ranked
applicable action the decoder constructs is executed; a rollout that proposes
an inapplicable action falls back to the next candidate in the beam, and if
none is applicable the rollout fails. Rollouts also end at the goal, at a
dead end, or at the step bound.

\emph{Plan quality} compares plan lengths on the instances that both the
policy and the reference planner solve. With $|\pi(t)|$ the policy's plan
length on instance $t$ and $|\rho(t)|$ the reference planner's,
\begin{equation*}
P(\pi) \;=\; \frac{\sum_{t \in \mathrm{solved}(\pi) \cap \mathrm{solved}(\rho)} |\rho(t)|}
                 {\sum_{t \in \mathrm{solved}(\pi) \cap \mathrm{solved}(\rho)} |\pi(t)|} .
\end{equation*}
Higher is better, and $P > 1$ means plans shorter than the reference. Because
$P$ conditions on what a system solves, a system with higher coverage is
scored on harder instances, so $P$ should be read within a column rather than
across columns, and coverage is the primary metric.

Coverage is measured with a revisit monitor, which resamples among the
decoder's applicable proposals when a greedy rollout re-enters a state it has
already visited. The monitor belongs to the execution harness and applies
identically to every system, including the untrained control. That is what
makes the control informative: it measures what the harness alone achieves
when the learned component contributes nothing, and it is the number the
policy's coverage should be read against.

\subsection{Renaming Invariance}
\label{app:invariance}

Invariance to renaming is a property of the construction rather than
something learned, and it is checked by a test that runs on every change to
the representation. Given a domain and a bijective renaming of its
predicates, action schemas, types, and objects, the test builds the graph for
the original and the renamed task and asserts that the node feature matrix,
the edge feature matrix, and the edge lists are identical. It covers both
typing conventions in the benchmark suite and asserts that a domain declaring
PDDL types and an equivalent domain spelling types as unary predicates
produce the same structure after type compilation.

\subsection{Compute and Runtime}
\label{app:compute}

All training and all evaluation ran on a single NVIDIA A40 GPU per run, one
run per GPU. Training one model on all eight domains takes seven to eight
hours. For comparison, the per-domain models of \citet{gabar} take roughly
two hours each, so covering the same eight domains costs about sixteen hours
and yields eight separate models rather than one.

Evaluation, not training, is the expensive half of a full experiment. Every
state of every rollout is featurized from scratch, and the largest test
instances are an order of magnitude bigger than anything seen in training, so
a single evaluation sweep over all eight test sets can exceed the cost of the
training run that produced the model. Anyone reusing this pipeline at larger
scale should expect that, and should look at the per-state graph construction
before looking at the network.

\subsection{Code}
\label{app:code}

The implementation is a single Python package built on PyTorch and PyTorch
Geometric, using PDDLGym to parse domains and problems and Fast Downward
\citep{fast_downward} to generate training plans. Each experiment is one YAML
configuration file naming the training domains, the representation, and the
evaluation domains, and a run is a single invocation of the entry point with
one such file, so the configuration files are a complete record of what was
run. The source, those configuration files, and the analysis scripts will be
released publicly under a permissive license on publication, with a pinned
dependency specification.
